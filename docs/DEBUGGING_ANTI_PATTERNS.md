## 🚫 反模式 1: 过度干预系统环境

### ❌ 错误做法
当遇到"新建愿望页面报错"这类小问题时:
1. 立即重启开发服务器
2. 删除 `.next` 缓存
3. 删除 `node_modules`
4. 清理 npm 缓存
5. 重装依赖
6. 修改端口配置
7. 检查文件句柄限制

### ✅ 正确做法
```
第1步: 看浏览器 Console 的完整错误日志
第2步: 确认前端调用的 API 路径
第3步: 检查对应 API 文件是否存在
第4步: 如果文件存在，检查代码逻辑
第5步: 只有在确认是环境问题时，才考虑重启
```

### 💡 判断标准
**何时需要重启/清理?**
- ✅ 新增了 API 路由，但访问 404
- ✅ 修改了环境变量
- ✅ 看到 "EMFILE: too many open files" 错误
- ✅ 看到 webpack 编译卡住
- ❌ **不应该**: 遇到任何代码 bug 就重启

### 📊 影响
- ⏱️ 时间浪费: 每次重启+重装 = 5-10 分钟
- 🎯 效率降低: 打断思路，增加焦虑
- 🐛 延迟发现: 真正的 bug 被系统操作掩盖

## 🚫 反模式 2: 不看日志就猜测问题

### ❌ 错误做法
```javascript
// 用户报告: "详情页内容截断"
// 错误反应1: "可能是 CSS 高度限制" → 修改 max-height
// 错误反应2: "可能是 API 的 token 限制" → 修改 max_tokens
// 错误反应3: "可能是端口问题" → 重启服务器
```

### ✅ 正确做法
```javascript
// 第1步: 要求用户提供 Console 日志
console.log('🔍 从数据库读取的 aiAnalysis 长度:', length);
console.log('🔍 aiAnalysis 最后100个字符:', content.slice(-100));

// 第2步: 对比不同阶段的数据
// - AI 生成: 892 字符
// - 数据库存储: 886 字符  ← 问题在保存环节!
// - 详情页显示: 886 字符

// 第3步: 精准定位保存逻辑
const aiAnalysis = streaming.snapshotContent(); // ← 检查这行
```

### 💡 关键原则
> **"数据不会说谎，日志是真相"**

1. ✅ 先看数据，再做假设
2. ✅ 对比不同阶段的数据
3. ✅ 使用二分法定位问题环节
4. ❌ 不要凭感觉修改代码

## 🚫 反模式 3: 同时修改多个地方

### ❌ 错误做法
当遇到内容截断问题时:
```typescript
// 同时修改了:
1. API 的 max_tokens: 2000 → 4000
2. 前端的 padding: pb-24 → pb-32
3. 流式缓冲区逻辑
4. 数据库查询逻辑
5. 重启了服务器
6. 清理了缓存
```

**结果**: 问题解决了，但不知道是哪个修改起作用的 😵

### ✅ 正确做法
```typescript
// 单点修改法:
1. 先定位问题 (通过日志)
2. 修改一个地方
3. 测试验证
4. 如果失败，回滚，尝试下一个
5. 如果成功，记录解决方案
```

### 💡 Git 最佳实践
```bash
# 每次修改一个问题，立即 commit
git add app/[locale]/wishlist/page.tsx
git commit -m "fix: 修复详情页内容截断问题 - 移除流式缓冲区"

# 如果修改失败，立即回滚
git reset --hard HEAD
```

## 🚫 反模式 4: 混淆不同场景的逻辑

### ❌ 错误做法
```typescript
// 把 Chat 的流式输出逻辑强加给详情页
if (viewOnly) {
  streaming.appendChunk('content', existingAnalysis); // ❌ 错误!
  streaming.finishStreaming();
}
```

### ✅ 正确做法
```typescript
// 根据场景选择合适的实现方式
if (viewOnly) {
  // 详情页: 静态内容展示
  setViewOnlyContent(existingAnalysis);
} else {
  // Chat页面: 流式输出
  streaming.appendChunk('content', chunk);
}
```

### 💡 设计原则
> **"不同的场景需要不同的解决方案"**

| 场景 | 需求 | 实现 |
|------|------|------|
| Chat 生成 | 实时显示，用户体验 | 流式输出 + 动画 |
| 详情页 | 快速加载，稳定可靠 | 静态内容 + 直接渲染 |
| 卡片列表 | 简洁预览 | 截断显示 + 省略号 |

## 🚫 反模式 5: 过度依赖 React State

### ❌ 错误做法
```typescript
// finishStreaming 后立即读取 state
streaming.finishStreaming();
const content = streaming.content; // ❌ 可能是旧值!
```

**原因**: React State 更新是异步的

### ✅ 正确做法
```typescript
// 使用 ref (同步) 或 snapshot (基于 ref)
streaming.finishStreaming();
const content = streaming.snapshotContent(); // ✅ 立即获取最新值
```

### 💡 State vs Ref 选择
| 数据类型 | 使用 State | 使用 Ref |
|---------|-----------|----------|
| UI 渲染 | ✅ | ❌ |
| 立即访问 | ❌ | ✅ |
| 回调函数 | ❌ | ✅ |
| 异步操作 | ❌ | ✅ |

## 🚫 反模式 6: 重复调用清理函数

### ❌ 错误做法
```typescript
// AI 生成完成时
streaming.finishStreaming(); // 第1次

// 保存时
streaming.finishStreaming(); // 第2次 ❌ 重复!
const content = streaming.snapshotContent();
```

**后果**: 第2次调用时，pending chunks 已经清空，可能丢失数据

### ✅ 正确做法
```typescript
// AI 生成完成时
streaming.finishStreaming(); // 只调用一次

// 保存时
const content = streaming.snapshotContent(); // 直接读取
```

## 📋 快速检查清单

### 遇到 Bug 时，先问自己:

- [ ] 我看了 Console 日志吗?
- [ ] 我对比了不同阶段的数据吗?
- [ ] 我定位到具体代码行了吗?
- [ ] 我只修改了一个地方吗?
- [ ] 我添加了验证日志吗?
- [ ] 我测试了修改效果吗?
- [ ] 我记录了解决方案吗?

### 如果回答"否"超过2个，停止修改，回到第1步!
